# IdeaSeek（科研论文到可验证 Idea 的多 Agent 平台）架构计划

## 1. 产品目标

用户在 Linux 服务器上进入一个研究方向目录，放入论文、补充材料和可选数据集，运行一条命令。平台完成论文盘点与证据化分析、研究脉络整理、候选 idea 生成与反证、受预算约束的小规模实验、基于结果的继续迭代，最后交付可复现代码、实验记录和研究报告。研究者审核后再把有希望的 idea 扩大实验。

目标不是保证“自动发现创新”，而是把研究者从手工筛读和试错中解放出来，并让每个结论、代码改动和实验结果可追溯、可复跑、可否证。

## 2. 核心设计决策

1. **把 DSH 当 Agent Runtime / 插件宿主，而不是科研数据库或唯一调度器。** DSH 的 Cordis 架构允许插件组合模型、工具和 Agent Loop；其 `ctx.agents` 提供 Agent 创建/恢复接口，也有 subagent 委派机制。用插件提供科研工具、CLI 命令和交互体验。
2. **科研工作流本身是持久化状态机。** 项目、论文、分析任务、comparison 候选与版本、idea 版本、实验运行及产物状态由平台服务保存。Agent 是可中断、可重试的任务执行者；不能把流程进度只存在会话历史里。
3. **首版采用单机模块化架构，不上微服务集群。** Linux 主机上用一个 CLI/控制进程、一个数据库、一个或多个 Worker 进程，以及隔离的实验容器。模块边界清晰，之后可以横向扩展 Worker。
4. **结构化证据是论文分析的中间产物。** Agent 生成的每个关键论断都要连接到论文页码/段落/表格；摘要不能替代原文证据。
5. **Idea 通过显式迭代循环产生。** 先从论文证据和已确认的 comparison 集合中抽取机制、假设、设计原则、失败边界和未解决矛盾，再生成多个候选；经过独立提出、团队讨论、相关工作反查、反方评审和可检验性筛选后进入实验。禁止把“方法 A + 方法 B”本身当作创新主张；任何组合都必须说明为什么两者在当前问题中形成新的机制或解决明确矛盾，并给出可被实验否证的预测。
6. **实验执行按不可信代码处理。** 生成代码在一次性容器中、以最小权限运行；资源、网络、数据挂载和预算有硬限制。
7. **实验协议由论文驱动自动综合，再由通用执行层约束和用户确认。** 平台应从论文实验、comparison 代码和用户数据中自己提出数据字段/样本单位、切分、泄漏检查、baseline、指标、smoke test、资源、消融和判据。领域适配器只提供必要的解析器、检查器和安全边界，不要求用户或平台预先手工编码完整科研方案。联邦学习模型异构可作为第一个真实验证方向，但不应阻塞通用协议生成器、论文管线和任务调度的开发。

## 3. DSH、模型层和 Python Worker 的边界

### DSH

使用 DSH 插件接入科研工具和工作流控制；使用 DSH Agent API 或 subagent 能力组织分析 Agent。不要为论文队列、长期任务恢复、GPU 排程和实验产物管理直接改 DSH 核心。DSH 当前提供 headless 单次任务入口和 SDK JSON-RPC，但 headless 适合脚本/单次任务，不应成为运行数小时工作流的唯一持久化机制。

DSH 是 developer preview 且兼容性仍会变化，工程上要固定 DSH 版本、固定插件 API 版本，并封装一个薄的 `HarnessAdapter`，避免业务层依赖其内部实现。

平台开发遵循 DSH 官方开发规范：科研功能以独立 Cordis 插件/Bundle 提供，使用公开的 Agent、Session、Tool、Subagent 和 profile 接口；通过配置 patch 组合科研工具和角色，不直接修改 DSH 核心包或复制一套 Agent Loop。每个插件声明版本和依赖，提供 schema、生命周期清理、错误事件和测试；开发环境固定 DSH commit/包版本，并为升级保留兼容性测试。业务工作流通过 `HarnessAdapter` 调用 DSH，任务数据库和 artifact 协议独立于 DSH，以便 DSH 版本变化时只替换适配层。

DSH Agent 的能力来自模型、上下文、工具注册和权限策略的组合，不是每个 Agent 天生拥有服务器全部权限。科研平台要为每个角色创建 capability profile：允许的工具、可读/可写路径、是否可联网、是否可启动容器、资源上限和是否能委派子 Agent。所有工具调用和权限拒绝都写入审计事件。

科研工具层至少提供这些受控工具：`paper_read`/`pdf_extract`、`knowledge_search`、`github_search`/`repo_metadata`、`git_clone`/`git_checkout`、`workspace_edit`、`shell_test`、`container_build`、`experiment_submit`、`run_log_read` 和 `artifact_publish`。`git_clone` 不是 DSH Agent 的天然能力，而是平台给 Comparison Discovery/Repair Agent 注册的工具；它只能把代码写入项目的 `upstream/` 或隔离缓存，记录 URL、commit、许可证和哈希，默认不能访问凭据或覆盖用户文件。GitHub/外部网络不可用时，平台应切换为用户提供的本地仓库或明确报告“无法获取”，不能假装已经检索。

#### 凭据与外部服务

凭据属于宿主/平台基础设施，不属于 Agent 上下文。启动前通过 `ideaseek setup` 配置模型 provider、GitHub 访问方式、外部学术索引（如启用）和实验镜像源；`ideaseek doctor` 只显示脱敏状态、权限范围和连通性，不打印 secret。优先使用 DSH 的 credential store/profile 或服务器的 secret manager；环境变量只作为受控部署方式，不能写入 `research.yaml`、PaperCard、prompt、日志、artifact 或 git。

- **模型 API**：配置 provider、endpoint、model 和 API key/凭据引用；按角色选择模型路由和费用上限。模型 key 由 DSH provider 在请求时读取，Agent 只能调用模型工具，不能读取 key 文件。
- **GitHub 公共仓库**：匿名读取优先；需要提高 API 限额时使用细粒度、只读的 token。公开仓库的 clone 不需要给 Agent 写权限。
- **GitHub 私有仓库/组织资源**：用户显式提供细粒度 token 或通过服务器上的 Git credential helper/SSH agent 授权；默认只授予指定仓库的 `contents:read`、metadata/read 等最低权限。平台应将 token 注入一次性 clone/fetch 进程，命令完成后清除，禁止把 token 传给模型或写进命令日志。
- **GitHub 写操作**：首版默认关闭。若未来需要提交修复或创建分支，必须单独启用、限定仓库/分支并在执行前要求用户确认；本平台的科研流程只需读代码和在本地工作副本修改。
- **网络策略**：论文/代码发现、依赖下载、镜像拉取和实验运行分别配置；默认实验容器禁网。所有外部请求记录域名/来源、时间、用途和失败原因，不记录 secret。

凭据失效、权限不足或网络关闭时，工作流进入可恢复的 `AUTH_REQUIRED`/`NETWORK_BLOCKED` 状态；`ideaseek next` 告诉用户缺少哪一种权限和配置命令，已完成的论文分析与实验结果不失效。Agent 不得自行索取、猜测或绕过凭据权限。

### Pi 与模型调用

不要同时运行两套 Agent 生命周期。首版直接使用 DSH 自带的模型 provider、认证、流式工具调用和模型路由，不引入 Pi。只有未来出现明确的 provider 覆盖或本地推理适配缺口时，才重新评估外部 Model Gateway；不把 Pi Agent Runtime 叠加到 DSH Agent Loop 上。Agent Runtime、工具和会话只由 DSH 负责一份。

模型供应商选择不应该改变科研流程。建立内部模型路由配置：按任务指定模型等级、最大并发、token/费用上限、超时和重试；论文提取可用便宜模型，综合评审或方案推演可用强模型；所有请求记录 provider、model、提示模板版本和用量。支持远程 API 与实验室本地 OpenAI-compatible/vLLM 服务。

### Python Worker

论文解析、科学文献工具、数据分析与机器学习生态主要在 Python；建议将其做成独立 Worker 包。TS/DSH 通过稳定的 JSON Schema 任务协议和数据库任务记录交接，不依赖同进程跨语言绑定。Worker 负责解析和实验执行，不自行充当第二个 Agent 平台。

## 4. 用户体验与 CLI

**当前工作目录就是一个研究项目。** 用户先在 Linux 服务器安装平台，在空目录中初始化工作区；平台创建标准子目录。用户自行把论文和数据集放进去，随后在这个目录带着科研问题启动工作流。平台不得要求用户先建立数据库项目、手工启动 Agent 或预先整理每篇论文。

```bash
mkdir continual-learning
cd continual-learning
ideaseek init
# 平台创建 papers/、datasets/、comparisons/、ideas/、reports/ 等目录
# 用户将方向论文放入 papers/；对比方法只需登记论文，代码可选
# 数据集放入 datasets/（或配置只读路径）
ideaseek setup          # 配置模型、GitHub/网络策略和实验运行时
ideaseek doctor         # 检查凭据引用、权限、Python/CUDA、容器和 GPU
ideaseek scan           # 扫描并整理用户随手放入的论文、代码和数据
ideaseek organize       # 预览/应用归类，不覆盖原始文件
ideaseek intake         # 查看待分类输入并按类型归档
ideaseek run --question "如何降低持续学习中的灾难性遗忘，同时保持新任务适应能力？"
ideaseek run --question "..." --ideas 3
ideaseek status
ideaseek next        # 检查当前工作区并告诉用户下一步操作
ideaseek attach         # 接入后台运行，实时查看事件流
ideaseek watch          # 持续监控，SSH 断开后可重新接入
ideaseek pause       # 可选；Ctrl-C 也会安全暂停
ideaseek resume
ideaseek cancel        # 取消当前 run，保留已完成产物和检查点
ideaseek continue      # 额度/凭据补充后从 checkpoint 继续
ideaseek report
```

`ideaseek init` 只创建目录、默认配置和 `README` 引导文件，不要求用户立刻按严格结构放文件。`ideaseek scan` 会递归扫描常见的 PDF、LaTeX、Markdown、代码仓库、压缩包、CSV/JSON/Parquet、模型配置和 README，按内容、元数据和代码特征建立输入 manifest；`ideaseek organize` 只在用户确认后创建索引、关联、软链接或平台管理的副本，绝不覆盖或移动原始文件。用户可以把论文、代码和数据随手放在项目根目录或默认子目录，平台先标记待确认对象。`ideaseek next` 是状态感知的下一步命令：根据当前目录文件、运行状态和未解决阻塞判断用户处于初始化、补论文/数据/对比方法、修复 baseline、确认实验协议、启动分析、恢复任务还是查看结果；它打印简短解释、缺项和下一条可复制命令，不会擅自开始高成本任务。`ideaseek run --question ...` 以当前目录为根。`--ideas N` 指定本次最多进入实验验证的候选 idea 数量；省略时由平台根据候选差异度、证据完整度、资源/预算和预计信息增益决定，默认先验证 1 个。随后平台扫描并哈希输入，检查模型、容器、存储和 GPU 条件，然后自动按阶段推进。它先分析小批论文形成校准结果；交互模式下用户确认方向后继续全量处理。服务器无人值守时，用户可在 `research.yaml` 预先设定方向范围、预算、自动继续策略和停止条件。平台运行期间输出阶段、已完成/排队/失败任务、资源使用与 idea 状态；SSH 断开或进程/服务器重启后，完成的检查点和产物保留，`ideaseek resume` 从未完成的最小任务单元继续，而不是从头处理项目。

推荐工作区结构：

```text
continual-learning/
  research.yaml           # 问题、模型、预算、数据和自动运行策略
  papers/                 # 用户原始 PDF、补充材料（只读输入）
  datasets/               # 用户数据集或指向已有数据集的软链接（只读输入）
  incoming/               # 暂时不确定类型的材料，只扫描/分类，不直接执行
  comparisons/             # 多个 baseline/对比算法，每个方法独立封装
    method-a/
      paper/               # 方法论文/补充材料，或关联 papers/ 中的论文（必需）
      upstream/            # 用户/平台找到的原始仓库快照（可选）
      worktree/             # 平台 Agent 修复/适配后的可运行副本
      method.yaml          # 论文关联、代码来源、入口、依赖、指标、许可/来源
      README.md            # 环境、运行命令与已知限制
    method-b/
      ...
  knowledge/                # 论文分析、数据与基线结论的持久化研究资料
    paper-cards/             # 每篇论文的结构化总结和原文证据位置
    syntheses/               # 分主题/方法的分层综合
    research-map.md          # 研究脉络、冲突证据和候选空白
    dataset-card.md          # 数据集结构、质量、许可和切分说明
    baseline-results/        # 对比方法的环境、运行记录和基线结果
    dataset-recommendations.md # 根据论文分析给用户的数据补充建议
  ideas/
    idea-001-*/
      idea.md              # 假设、相关工作、新颖性边界、判据、版本历史
      src/                 # 该 idea 独立的代码与配置
      data/                # 从原数据派生、可重建的小规模切片/缓存
      experiments/         # 仅属于此 idea 的运行、日志、指标和产物
      README.md            # 如何复现及当前判断
    idea-002-*/            # 不同 idea 完全分开，不共享可变代码目录
  reports/                 # 校准、论文综合、中期和最终报告
  .research/               # 数据库、解析文本、索引、任务队列、缓存和审计记录
```

每个 idea 有独立目录、代码版本和实验历史。实验记录必须指向唯一的 `idea_id`、idea 版本、代码 commit/hash、数据切分版本和 `run_id`；一次 idea 的代码优化不得悄悄修改另一个 idea。用户查看最终报告时，可以直接定位到 `ideas/idea-00N-.../`，并通过该目录的 README、配置和结果复现实验。

`comparisons/` 中的方法是独立、版本固定的对照对象，不属于任何 idea，也不作为唯一代码模板。用户可以提供 comparison，也可以只提供论文；平台还可以在论文分析阶段自动发现并补充 comparison。自动发现的候选先写入 `comparisons/_candidates/`，记录来自哪些论文、为什么与当前问题/数据相关、预计资源、代码可得性和缺失信息；通过筛选后才提升为 required comparison。用户若提供仓库，平台记录 URL、分支/tag/commit、许可和导入哈希；原始快照放在 `upstream/`，Agent 只在 `worktree/` 修复或适配。用户未提供代码时，平台先按允许的来源定位官方实现；若没有可用官方实现，则由 Baseline Reproduction Agent 根据论文方法、公式、伪代码、实验设置和统一数据协议在 `worktree/` 实现重现版本。两种结果必须分别标记为 `official-code` 与 `paper-reimplementation`，报告中不能把后者称作作者官方实现，也不能把它的结果当作严格的官方复现。

无论代码来源是什么，Agent 都要输出实现依据、缺失细节、与论文设置的偏差、代码 diff、依赖和复现状态。论文中无法确定的细节必须列为假设并影响置信度；平台可以用有限敏感性实验检查这些假设，但不能凭空补细节后宣称方法已被准确复现。`comparisons/` 代码只读用于参考项目布局、数据接口和实验配置；新方法始终写入自己的 `ideas/<id>/src/`。

平台不得静默覆盖 `papers/`、原始 `datasets/`、`comparisons/` 或用户已有文件。每次 run 固定一份输入快照清单（路径、内容哈希、版本与读取时间）；运行中若用户增删/修改输入，不得悄悄把新旧结果混在同一 run，应提示并选择继续使用原快照，或显式创建新 run 并仅失效受影响的下游节点。论文总结与研究综合以结构化记录保存在工作流数据库，并导出到 `knowledge/` 供检查、检索与版本管理；PDF 原件仍留在 `papers/`。数据分析和切分只在 idea 自己的 `data/` 派生产物中完成，并记录生成脚本、输入哈希和切分方案；可删除重建，不能冒充原始数据。重复运行做增量处理。`papers/`、`comparisons/` 和 `datasets/` 都按内容哈希、路径和元数据建立索引。新增论文只创建未分析的 PaperCard 任务；已有论文若文件哈希和解析/prompt/schema 版本不变则复用原结果。新增或变化的数据集只生成新的 dataset snapshot、数据质量检查和受影响 baseline/idea 实验任务，不重新执行不依赖该数据的论文分析。新增 comparison 只补做该方法的发现、实现和验证。`ideaseek status` 与报告显示本次 run 新增、复用、失效和待验证的对象数量。\n\n### 引导式输入与自动整理\n\n用户通常有三类材料：方向论文、部分 comparison 的论文/代码、一个或多个尚未整理的数据集。平台给出三个明确入口：`papers/`、`comparisons/<method-id>/`、`datasets/<dataset-id>/`；不确定类型的材料先放 `incoming/`。这样用户有清晰的推荐路径，同时不要求一次完成严格整理。\n\n`ideaseek scan` 默认只扫描这些入口和 `incoming/`，不扫描 `.research/`、`ideas/`、日志和实验产物；用户可以用 `--path` 显式添加其他目录。`ideaseek intake` 将候选文件分组并要求用户确认，`ideaseek organize --apply` 只创建索引、软链接或平台副本，原始文件永不移动或覆盖。\n\n### 宽松输入与自动整理\n\n用户不需要严格按“一篇论文一个文件夹、一个方法一个目录”的规则准备输入。Workspace Intake Agent 负责：\n\n- 通过 PDF 元数据、标题、作者、DOI、README、`requirements.txt`/`pyproject.toml`、训练入口和数据文件特征识别论文、代码、数据和补充材料；\n- 通过内容哈希去重，识别同一论文的不同 PDF、同一仓库的 clone、压缩包和工作副本；\n- 将可能属于同一 comparison 的论文、代码、配置和 README 聚成候选组，显示置信度和依据；\n- 将数据文件按格式、字段、标签、样本规模和目录上下文聚成 dataset candidate，标记 train/valid/test 的不确定性；\n- 生成 `knowledge/input-manifest.json`、`knowledge/input-review.md` 和待确认清单，用户确认后再建立 comparison、dataset 和论文角色关联；\n- 对歧义对象保留原路径和哈希，不能自动移动、覆盖、删除或把不确定文件当作已验证输入。\n\n平台管理的规范目录是内部索引和工作副本，不是用户必须遵守的上传协议。用户可以运行 `ideaseek organize --apply` 应用整理，也可以只保留 manifest，让平台通过原路径读取。任何软链接或副本都记录来源路径、哈希和创建时间。平台默认不下载大型数据集，只在用户提供或授权挂载后处理；根据论文中的常用数据集和当前任务生成 `knowledge/dataset-recommendations.md`，告诉用户可补充哪些数据、用途、字段、许可和预期验证价值。

`ideaseek next` 的输出应像一个可执行的向导，例如：

```text
当前阶段：BASELINE_REPAIR
阻塞：comparisons/method-b 仍有 2 个 required 检查失败
已完成：论文 1000/1000；数据集检查；method-a 复现
下一步：查看修复日志，或让平台继续有限修复
建议命令：ideaseek baseline repair --method method-b
```

当所有 required 对比算法通过且实验协议已确认时，它才会提示进入 idea 阶段；如果有用户操作需要完成，它显示具体目录、文件和命令，而不是只输出“任务未完成”。

### 实时交互、后台运行与重新接入

`ideaseek run` 默认以前台交互模式启动 workflow supervisor，持续输出可读事件：当前阶段、Agent 角色、任务/论文/方法/idea 标识、工具动作摘要、完成数量、失败与重试、模型/API 用量、GPU/CPU/内存占用、队列和预计等待原因。输出使用事件序号和 `run_id`，终端断开后不丢事件；`attach` 从最后已读序号继续，必要时先回放事件再接收实时事件。日志和原始工具输出写入文件，终端只显示脱敏、限长摘要，并提供任务 ID 供用户查看详情。

```bash
ideaseek run --question "..."                 # 前台实时交互
ideaseek run --question "..." --detach        # 后台启动并立即返回 run_id
ideaseek attach --run <run_id>                 # 重新接入后台任务
ideaseek watch --run <run_id>                  # 持续观察直到完成/暂停/失败
ideaseek events --run <run_id> --since 120     # 回放最近事件
ideaseek status --run <run_id> --detail        # 查看阶段、阻塞和资源明细
```

后台模式由项目级 supervisor/worker 进程负责，不依赖用户终端、SSH 会话或 `nohup` 的偶然行为；PID、启动参数、版本、日志和心跳写入 `.research/daemon/`。同一项目的第二个 `run` 默认拒绝或要求显式创建独立 run，避免多个进程写同一份工作区。服务器重启后 supervisor 根据 checkpoint 自动恢复，用户用 `attach` 接回。

实时显示的是可审计的外部行为和结果摘要，例如“Paper Extractor 完成 18/50”“Baseline Repair Agent 正在分析 ModuleNotFoundError”“GPU 0 实验排队，预计需要 8 GiB 显存”，不输出模型隐藏的逐 token 思维过程。需要用户确认时暂停在明确的 approval gate，显示原因、影响、相关文件和可执行的继续命令。

暂停分为两种：`pause` 停止领取新任务，并让当前任务在安全边界保存 checkpoint 后结束/取消；`pause --hard` 在用户明确指定时终止可中断任务，标记当前 run 需从最近 checkpoint 恢复。`resume` 重新探测环境、恢复租约和队列；`cancel` 停止整个 run，但保留所有已提交 artifact、日志、代码 diff、论文卡片、baseline 结果和实验检查点。正在运行的不可中断容器可能需要等待超时，状态必须显示这一点。

## 5. 单机架构

```text
CLI (Python Typer 或 TS Commander，选择一种主入口)
  ├── Project Manager / Config / Run Controller
  ├── Workflow Supervisor + Event Bus (实时事件、后台生命周期、attach/replay)
  ├── Workflow DB (首选 PostgreSQL；单人快速原型可 SQLite WAL)
  ├── Artifact Store (项目目录，内容寻址与哈希清单)
  ├── DSH Adapter (Agent 生命周期、工具与模型会话)
  ├── Python Workers
  │     ├── PDF ingest / 文献解析 / 索引
  │     ├── paper & idea task workers
  │     └── experiment runner
  └── Container runtime (Docker/Apptainer，按服务器支持选择)
```

### 持久化对象

- **Project**：研究方向、输入目录、配置和全局运行状态。
- **Document**：文件哈希、元数据、解析版本、章节和证据片段位置。
- **Task**：类型、输入引用、状态、租约、重试次数、错误、输出引用、消耗。
- **PaperCard**：每篇论文的结构化事实与证据引用。
- **Synthesis**：主题聚类、方法谱系、争议、未解决问题及引用。
- **Idea**：带版本的假设、相对已有工作的差异、预期贡献、失败条件、实验判据和评分分项。
- **IdeaWorkspace**：idea 专属代码目录、git 分支/提交、数据切片和依赖环境引用。
- **ComparisonMethod**：对比方法的论文关联、源码版本/hash、运行入口、依赖、数据/指标适配器、许可和复现状态。
- **ExperimentRun**：代码 commit/hash、镜像、数据版本、配置、种子、GPU/CPU/内存、日志、指标和产物。
- **Decision/Event**：状态变更、人工决策、Agent 使用模型与工具的审计事件。
- **AgentCapabilityProfile**：角色允许的模型路由、工具集合、文件/网络/进程权限、资源上限和审批策略。
- **RunEvent**：带顺序号的阶段、任务、工具摘要、资源、审批、错误和产物事件，支持持久化回放与实时订阅。

生产方向项目优先 PostgreSQL 做工作流状态/任务队列；原始 PDF、解析产物和运行文件保存在文件系统或对象存储，数据库只存元数据与引用。单机原型可以 SQLite WAL，但队列必须有原子领取/租约/心跳/超时回收语义。向量索引是可重建派生数据，不能作为原始证据库。

## 6. 端到端工作流

每次执行写入 `run_id`，整个工作流是可恢复的有向无环图，包含分支与循环：

### 阶段 A：预检与盘点

1. 校验目录、磁盘空间、PDF 可读性、数据集路径、容器运行时和模型连接；读取 Python 版本、依赖/容器镜像可用性、CPU 核数、系统内存、磁盘余量、GPU 型号/数量/显存和当前显存占用。
2. 检查 PyTorch/CUDA 或项目声明的框架是否可用，CUDA runtime、驱动和容器 GPU passthrough 是否兼容；检查 GPU 上是否已有其他进程，切勿假定“看到 GPU”就代表可独占使用。探测结果带时间戳，并在实验提交前刷新。
3. 读取 `research.yaml`，记录研究问题范围、用户给定的数据集、允许的模型/网络、并发与总预算、实验最大轮数和每个 GPU/项目的资源上限。
4. 对文件做哈希、元数据抽取和去重；检测损坏 PDF、重复版本和疑似缺失补充材料。
5. 产出输入清单、环境/资源能力报告和预计工作量；配置不足时尽早退出并指出要补充的字段。
6. 明确语料边界：用户目录是唯一知识源，还是允许查询外部学术索引/论文元数据。若允许外部检索，记录检索日期、查询式、数据库和结果清单；若不允许，报告必须说明“新颖性只针对已上传语料评估”，不能暗示已完成全领域查新。

### 阶段 B：论文语料构建

1. 解析全文、章节、参考文献、图表/表格标题与页码；对扫描件尝试 OCR。
2. 将解析文本切为可引用片段，保留页码、章节、表格/图号及原文件哈希。
3. 构建全文检索和向量检索；保存解析器版本与质量状态。
4. 聚类与主题分类用于任务分批，但不丢弃任何论文；抽样核验解析质量，低置信文档标记人工复核。

### 阶段 B2：数据集识别与验证准备

1. 清点 `datasets/` 和配置的只读路径，识别文件格式、样本数、字段/标签、类别分布、缺失/重复值、许可信息和潜在敏感字段；解析失败时报告具体文件和原因，不猜测数据含义。
2. 由数据分析 Worker 生成 dataset card 与数据质量报告；Protocol Synthesis Agent 再结合研究问题、论文实验范式和 comparison 代码入口提出 `ExperimentalProtocolProposal`，覆盖验证任务、字段/样本单位、切分、泄漏检查、指标、基线、最小样本规模、smoke test、资源、消融和支持/否证判据。可选领域解析器/检查器只提供必要约束。系统自动推断出的标签含义、样本单位、泄漏分组、指标方向等必须附来源/置信度；存在实质歧义时展示候选解释并请求用户确认，不能只从文件名/列名猜定并直接用于正式结论。
3. 平台默认在原始全量数据只读的前提下创建 `smoke`/`quick`/`standard` 派生切片；不得为追求短时结果而任意丢样本或破坏类别/时间/主体分布。按领域规则选择分层、时间、组别、域、客户端或留一划分；保存切分 manifest、统计摘要和随机种子。用户后续的全量实验只通过 `handoff` 交付配置、命令和资源建议，不在 IdeaSeek 内执行。
4. 原始数据只读。禁止把测试集反馈用于迭代调参；小数据不足以形成可靠确认集时，报告直接说明统计能力和外推局限，并可改为交叉验证、重复实验或要求补充数据。
5. 扫描 `comparisons/` 中的方法，读取或生成方法清单：上游仓库 URL/commit、关联论文、源码入口、环境/依赖、训练与评估命令、支持的数据格式、指标和许可证。目录内每个方法默认是 required；先在隔离环境做依赖检查和 smoke test，再标记为“可运行”“需修复/适配”“不可运行/缺文件”；不能因目录存在就假设它是有效 baseline。
6. Protocol Synthesis Agent 根据论文、comparison 实验脚本和 dataset card 生成统一实验协议草案；Leakage/Validity Checker 检查任务定义、数据切分、预处理、指标方向、种子、统计汇总和资源公平性。用户确认必要歧义后锁定协议版本，各方法通过薄适配层接入共同协议，适配不得改变算法核心。分别记录原论文报告值、本地复现值和复现差异。

### 阶段 C：论文分析与综合

1. 先用元数据/全文检索把语料组织成主题簇与可追溯分片，再把论文分成有界大小的提取任务。单篇过长论文按章节/图表拆子任务，子任务共用 document id 与证据位置；不能把 1000 篇全文放进一个 Agent 上下文。批次大小依据上下文窗口、输入长度和任务类型动态控制，不固定“一篇一个 Agent”或“一 Agent 一簇”。
2. 论文提取采用 map/reduce：有限数量的 Paper Extractor 并发领取任务，逐篇或小批次生成固定 schema 的 PaperCard；主题 Agent 只读取该主题卡片和按需检索的原文证据，形成主题综合；领域综合 Agent 再对比主题综合，形成研究地图。每层结论保留到下层卡片和原文片段的引用链。
3. 汇总不能只靠逐层摘要传话。全局 Agent 对关键主张、方法差异和候选空白必须回到论文索引做定向检索，抽取原文证据复核；若发现摘要遗漏或冲突，回到对应论文/簇补充分析。
4. 每篇论文最终生成固定 schema 的 PaperCard：研究问题、假设、方法步骤、关键设计及动机、复杂度/依赖、数据集、指标、基线、结果、消融、局限和可复现性。
5. 所有关键字段保存证据跨度；无法证实时显式输出 `unknown`，不允许编造。
6. 校验器检查 JSON/schema、引用是否存在、数值与单位是否对应原文；失败则有限次修复或进人工队列。
7. 按主题/方法/数据集形成小组综合；跨组综合总结方法谱系、性能权衡、结论冲突、常见假设与未解决问题。
8. 对引用和关键数字做第二次独立核验；生成可搜索的研究地图和带证据的综合报告。

`papers/` 是总研究语料库，包含用户上传的综述、方法和对比算法论文；`comparisons/<id>/paper/` 可以通过文件哈希关联到同一份论文，不复制第二份全文。论文在语料中的角色（普通参考、required comparison、候选 baseline、数据集论文等）是元数据标签，同一篇论文可以同时属于总语料和一个 comparison。这样 idea Agent 能从完整研究脉络学习，baseline 流程又能按明确的 comparison 清单逐项验证。

不要默认对 1000 篇论文启动 1000 个长期 Agent。**论文数量决定任务总量，并发度由机器/API 配额决定。**任务按论文和小批次入队，有限 Worker 拉取；上下文只放当前论文/小批次和必要检索片段。局部失败只重跑失败任务，成功的 PaperCard 缓存复用。

分析结果要从第一篇论文开始持久化，不能只留在 Agent 会话：每篇论文生成结构化 PaperCard（数据库中的权威记录 + `knowledge/paper-cards/` 的可读导出），每完成一个主题簇就更新其综合记录和证据引用，最终生成 `knowledge/research-map.md`。记录输入文件哈希、解析器与 schema/prompt 版本和证据定位。修订保留历史；增量运行只重算输入或版本确实变化的记录。

这里的“读过并学到”指**在本项目中建立可追溯的检索与结构化知识库**，不是自动微调或永久改变底层模型。后续 idea Agent 通过检索 PaperCard、主题综合和原文证据获取知识。跨项目复用默认关闭，只有用户显式选择导出/共享时才复用，避免私有语料意外泄漏。

### 阶段 C2：先复现对比方法，建立可信基线

在 idea 生成之前，根据数据集分析、论文研究地图和 `comparisons/` 清单确定共同评测协议，逐个准备环境并运行对比算法。用户没有提供完整 comparison 时，平台先自动补齐候选：

1. Comparison Discovery Agent 从 PaperCard、主题综合、论文中的实验表格/基线列表和数据集相关论文中抽取候选方法，合并同名/同源版本，区分“核心必比方法”“强基线”“简单基线”“消融/组件对照”和“仅作背景参考”。
2. Candidate Reviewer 按当前研究问题、数据任务、时间范围、论文中使用频率、方法代表性、是否有可运行定义和预计成本打分，并检查候选是否已经在 `papers/` 语料中出现。候选保存在 `comparisons/_candidates/`，来源论文和筛选理由可追溯。
3. 平台将通过筛选的候选加入 `comparisons/` 并标记来源为 `discovered`；用户可以在配置中设置自动接受、先展示候选再接受，或只接受用户指定集合。自动接受也必须受总数量、费用、GPU 时间和网络访问配额限制。
4. 对每个 accepted/required comparison，按“用户代码 → 允许来源的官方代码 → 论文重实现”的顺序准备实现，再进入下面的修复、协议适配和运行流程。找不到代码、论文细节不足或许可证不允许使用时，方法保留为 `blocked`/`reference-only`，不能伪装成已验证基线。

5. 在隔离环境验证依赖和入口，跑极小样本 smoke test。失败后 Baseline Repair Agent 根据完整日志诊断常见问题：Python/依赖冲突、过时 API、硬编码路径、数据格式、启动命令、设备选择、评估脚本和平台接口不兼容。
6. Agent 在 `worktree/` 中提出最小修复，保留结构化 patch/diff、原因和测试；重新构建环境并运行。修复循环次数、时间和网络/安装权限受预算限制；每轮失败原因写入记录，避免反复盲修。原 `upstream/` 不改动，修改始终可审查和回退。
7. 将改动分类为环境/依赖修复、路径/启动修复、数据/评估适配或算法语义改动。前三类可在沙箱中自动尝试；任何可能改变模型结构、损失函数、训练策略、数据使用或指标定义的改动必须显式标成算法修改，不得继续作为原 baseline 的复现结果。用户需确认是否将其作为“修订版对比方法”单独评测。对于 `paper-reimplementation`，还要记录“论文明确内容”和“平台实现假设”，并单独标注复现置信度。
8. 修复后先跑原仓库测试（若有）、小样本 smoke test，再在用户数据的合法小规模切分上跑基线；记录上游 commit、patch hash/diff、环境锁文件、数据哈希、指标、日志和资源用量到 `knowledge/baseline-results/`。
9. 将结果与对比论文的设置和指标核对，标记为“原样成功”“兼容修复后成功”“重实现成功”“修订算法后成功”“部分复现”“协议不一致”“环境阻塞”或“无效运行”；代码能启动不等于基线有效。
10. 默认要求所有 required comparison 都在当前数据/指标协议下有一个可运行结果并通过合理性检查，才进入 idea 生成阶段。对于官方代码，这是官方实现经过兼容修复后的结果；对于仅有论文的方法，这是平台重实现经过检查后的结果。全部失败或仍有方法缺少可运行结果时，平台停在可恢复的 comparison 阶段，不生成科研 idea，除非用户显式排除该方法或开启“无有效对照的探索模式”。
7. 用户若确认某个方法不适用于当前任务、许可不允许运行或决定暂不比较，必须显式设为 `required: false`/排除并填写原因；平台在报告中列出排除项及影响。Agent 不能静默跳过。所有剩余 required 方法通过门槛后才继续。
8. 把每个 required baseline 的分数、误差特征、速度/显存成本和实现限制加入研究上下文。后续 idea 要针对已测 baseline 的已观察局限提出改进，并最终与所有 required baselines 对齐比较。

这里的快速小规模验证用于排除明显无效方向，不冒充论文规模的正式复现。基线快跑值与论文结果不一致时保留差异说明；后续比较尽量保证新方法与 baseline 的数据、预处理、指标和计算预算可比。

### 阶段 D：候选 Idea 生成与筛选

先从研究地图提出多条彼此不同的候选方向，而不是让一个汇总 Agent 一次拍板。平台先构建“设计原则与机制库”：从论文中归纳方法试图改变什么、通过什么机制改变、依赖什么条件、在哪些情况下失败、与哪些方法结论冲突。再从研究问题的瓶颈/矛盾出发生成候选。候选先在 `quick` 规模做低成本区分性实验，通过门槛后才晋级 `standard` 场景；平台默认不让每次代码或参数修改触发全量运行。候选必须通过“机制链检查”：问题 → 观察/假设 → 介入机制 → 预期可观测变化 → 与 baseline 的差异 → 否证条件。缺少机制解释的表面模块组合降级为待讨论草案，不进入自动实验。

Idea 生成模拟科研小组，而不是单个模型连续改写：至少有独立的 Idea Generator、Mechanism Analyst、Novelty Challenger、Experiment Designer 和 Synthesis Lead。各角色先独立提出或分析，再通过结构化讨论交换证据和反例；Synthesis Lead 只汇总有证据支持且彼此差异清楚的候选。团队可以保留互相竞争的解释，不强行制造共识。

每个 Idea Card 至少包括：

- 可检验的研究假设与目标问题；
- 与最接近的相关工作逐项对比，并给出证据位置；
- 新颖性主张及其不确定性；
- 机制解释、预期收益与边界条件；
- 最小验证所需的代码、数据、基线、指标和消融；
- 可能否证该假设的结果、成本、风险和停止条件。
- 机制链及其与论文设计原则的对应关系；
- 为什么不是已有工作的直接重述或任意模块拼接；
- 若使用多个已有组件，各组件关系是必要机制、替代解释还是工程实现，去掉任一组件时预期会发生什么。

筛选流程：机制抽取 → 问题矛盾定位 → 独立候选生成 → 结构化小组讨论 → 相关工作检索 → 相似方法反例搜索 → 独立反方 Agent 尝试推翻 → 可行性/资源审查 → 最小区分性实验设计 → 小实验优先级排序。实验优先设计能区分竞争解释的诊断和消融，而不是只追求总指标提升。评分拆成机制合理性、新颖性证据、技术可行性、可测试性、潜在影响、成本和风险；总分不取代证据和研究者判断。保留被否决 idea 及理由，后续结果可以重新激活或关联它们。

加入两个明确的人工检查点：正式启动实验前，用户确认候选、数据使用方式和预算；最终交付前，用户可标记“有用/无用/已有工作/实验无效”并附原因。平台可以在无人值守配置下继续跑受限实验，但不得突破事先配置的成本、资源和轮次上限。用户反馈作为带时间和作者的事件保存，不能悄悄覆盖 Agent 生成的判断。

### 阶段 E：实验闭环与 Idea 更新

基于 `knowledge/research-map.md`、`knowledge/dataset-card.md` 和已验证的 `knowledge/baseline-results/` 生成用户要求数量范围内、机制或路线不同的候选 Idea；数量不能只按模型一次吐出多少条决定，而要结合候选差异度、证据完整度、代码/数据可行性和可用实验预算筛选。每条候选指出由哪些论文证据启发、针对哪个 baseline 局限、如何在当前数据上检验。每个入选 idea 分别创建独立目录、代码工作树与实验规格。

启动实验前，Capacity Planner 将刚探测的 GPU/CPU/内存/磁盘、现有负载、Python/CUDA 环境、每项实验的预计资源、idea 优先级和项目配额合并计算可准入的并发数 `N`。`N` 取受用户上限、GPU 显存余量、CPU/内存余量、并行 Worker 上限和预算共同约束的安全值；无法可靠估算的实验先以低并发 smoke test 测量，再更新估值。实验过程监控实际资源，遇到 OOM、显存/温度/资源争用或剩余预算不足时暂停新任务、排队或终止符合策略的任务，并记录原因。禁止为了“并行”把 GPU 超额分配。

平台可并行推进多个 idea：不同 idea 的设计、实现与 CPU/数据准备任务并行；GPU 实验通过统一调度器按资源请求排队/并发。资源不足时安全等待，而不是超额挤占服务器。可并行的程度由实时 GPU/显存、CPU、内存、Python 环境和用户配置决定，不承诺所有实验同时启动。

每个 idea 有独立的 Agent 上下文、代码分支、依赖环境、数据派生产物、指标与运行历史；只读共享原始语料、原始数据和公共基线。需要公平比较时，各 idea 使用同版本数据清单、预先定义的切分和匹配的计算预算。实验不能只在一个随机切片上跑一次：Scenario Planner 根据论文证据、数据特点、baseline 失败边界和 idea 机制生成分层实验组合，从 L0 工程有效性、L1 机制验证、L2 多种子稳定性、L3 场景鲁棒性到用户有数据时的 L4 跨数据/外部验证逐步推进。资源不足时先完成能区分候选机制的最小场景，并明确未覆盖范围。一个 idea 的每轮代码修订形成新版本；结果分析 Agent 读取该 idea 的历史结果，决定继续优化实现、修改假设生成新版本，还是停止。换方向时创建新 idea 并链接其来源，不能覆盖原有假设或把不同 idea 的结果混在一起。每个 idea 可独立进入下一轮，其他 idea 不必等待它完成。各自的实验规格再启动隔离执行：

1. 每个 Idea 的 Code Agent 从该 idea 的实验规格编写代码、配置、测试和运行说明，限定写入自己的 `ideas/<id>/src/` 工作区。它可以只读检查 `comparisons/` 的接口、目录结构和配置约定，借鉴工程风格；算法设计必须由 idea 规格和相关工作证据支撑。Agent 尽可能复用公共数据适配接口，不得直接改写 comparison 源码、系统 Python 或全局 CUDA 环境。
2. 用独立锁文件/容器镜像建立可复现的 Python 环境；idea 与 comparison 可以有不同依赖环境，但评测协议和数据版本一致。复用预构建缓存时校验依赖哈希。外部依赖安装按网络策略执行，记录精确版本和安装日志。若当前 Python、框架或 CUDA 不兼容，先尝试在容器内选择兼容环境；仍失败则将其报告为环境阻塞，不绕过宿主限制。
3. 代码先经过静态检查/单元测试（适用时）、数据与指标检查、极小样本 smoke test 和资源测量；只有通过门槛才进入 GPU 实验队列。失败时分辨代码错误、环境错误和假设问题，修复后重新验证，避免把程序崩溃误判为科学假设失败。
4. 先验证数据读取、指标实现和基线复现；比较候选 idea 时尽量在共同协议下运行用户提供的多个 comparison 方法。至少有可信基线成功运行后才报告相对效果；若基线均无法复现，可以报告 idea 绝对结果，但必须标明“缺少有效对照，不能据此断言优于已有方法”。
5. 固定数据拆分和种子。防止测试集泄漏；调参仅用训练/验证划分。按任务需要使用多个种子或报告方差，避免把单次噪声当成有效提升。
6. 每次运行保存代码版本、容器镜像、Python/CUDA/框架版本、完整命令、配置、硬件和可见 GPU、环境变量白名单、日志、指标和模型产物。
7. 结果分析 Agent 对照预先登记的判据，说明成功、失败、不确定或实验无效，并引用原始日志/指标。
8. 失败分类：实现错误、环境/数据问题、假设不成立、效果不足、资源不足、证据不足。修代码与改科学假设是不同操作，分开记录。
9. 若有诊断价值且预算允许，生成一个有明确依据的下一轮变更（idea 版本 + 实验计划），而非任意搜索超参数；否则停止并说明证据。
10. 达到预算、连续无信息增益、数据质量阻塞、场景组合的预设覆盖目标或候选通过标准时停止。平台给出停止依据，不无限循环；通过 L1 不得写成跨场景有效，通过 L3/L4 也要报告未测试分布。
11. 严格区分探索集与最终确认集。若同一验证集被多轮 idea/超参数选择反复使用，结果会产生选择偏差；确认性结果应使用预留数据、独立种子或新数据，并报告尝试次数。涉及随机任务时记录重复次数、均值/方差或置信区间，并报告所有预先登记的主指标，不能只挑有利结果。

实验接口采用统一 `ExperimentSpec`/`RunResult` schema。首版只支持一个约定式 Python 项目接口（如 `train.py`/配置文件/metrics.json），后续再加 PyTorch Lightning、Hugging Face 等适配器。

## 7. Agent 角色与合同

Agent 是按任务配置的角色，不必每个角色长期驻留，也不一定使用不同模型：

- **Paper Extractor**：一篇/一个小批次论文，输出 PaperCard + evidence。
- **Evidence Checker**：核对来源、页码、数字和引文支持关系。
- **Synthesis Analyst**：按问题整理方法对比、演进和冲突证据。
- **Comparison Discovery Agent**：从论文实验、数据集论文和研究地图发现应比较的方法，去重、分类并说明纳入依据。
- **Candidate Reviewer**：审查自动发现的 comparison 候选、成本、代表性、许可证和复现可行性，决定 required/reference-only/blocked 状态。
- **Idea Generator**：提出有区分度的候选 Idea Card。
- **Novelty Challenger**：主动找最接近工作、反例和已有先例。
- **Experiment Designer**：把假设变为有判据的最小实验与消融矩阵。
- **Code Implementer**：只在指定的 `ideas/<idea-id>/src/` 中改该 idea 的代码，必须走版本控制差异审查；不能跨 idea 共用可变工作树。
- **Baseline Repair Agent**：在 comparison 的隔离 `worktree/` 中诊断和修复环境/接口问题，输出最小 diff、测试证据和语义变更分类；不得覆盖 `upstream/` 或隐瞒算法改动。
- **Baseline Reproduction Agent**：当只有论文没有可用官方代码时，根据论文证据实现可审计的重现版本；明确记录实现假设、缺失细节、与论文的偏差和复现置信度，不把重实现冒充官方代码。
- **Result Analyst**：结合实验日志判断支持/否证/不确定，建议下一步。
- **Workflow Supervisor**：汇总状态、路由阶段和请求澄清；不能绕过预算、安全策略和任务状态机。

各角色以 JSON Schema 输出，保存 prompt/schema 版本。共享的是证据库、PaperCard、Idea/Run 记录；不是共享无限增长的对话上下文。Agent 之间交接通过对象 ID 和短摘要完成。

角色能力示例：

| 角色 | 可用能力 | 明确限制 |
|---|---|---|
| Paper Extractor / Evidence Checker | 读取 PDF、OCR/解析工具、全文/向量检索、写 PaperCard | 只能写 `knowledge/` 临时/结果区，不能执行任意 shell 或修改原始输入 |
| Synthesis / Idea Agent | 检索 PaperCard、研究地图、comparison 和实验结果；写综合/Idea Card | 不直接改 baseline 或启动未登记实验 |
| Comparison Discovery Agent | 读取论文实验信息、查询允许的学术/GitHub 元数据源、创建候选 comparison | 外部下载必须经过网络策略、来源/许可记录和配额；只能写 `_candidates/` |
| Baseline Repair / Reproduction Agent | 在隔离 worktree 编辑、安装锁定依赖、运行测试和 smoke test、读取日志 | 不能写 `upstream/`、原始数据或系统环境；算法语义改动单独标记 |
| Code Implementer | 在对应 idea 目录读写代码、运行静态检查和受限测试 | 不能跨 idea 写入，不能绕过实验队列直接占用 GPU |
| Experiment/Result Agent | 提交 ExperimentSpec、读取运行日志/指标、分析结果 | 只能由执行服务运行容器，不能直接取得宿主权限 |
| Workflow Supervisor | 查看状态、创建/重试/暂停任务、请求用户确认 | 不能绕过预算、权限、required comparison 门槛或数据快照 |

“深度思考”由任务选择的模型、上下文证据、推理预算和允许的迭代次数共同提供：论文单篇提取可以用较低成本路由，跨主题综合、comparison 选择、代码修复诊断和 idea 反证使用更高推理预算。Agent 可以调用检索工具多轮查证，但每次调用仍受任务预算和 checkpoint 约束。

## 8. 调度、可靠性与多 GPU

数据库任务队列支持优先级、并发上限、资源需求、租约和失败重试。任务至少区分 CPU-heavy（解析）、模型 API（受并发/费用限速）、本地推理（显存资源）和实验 GPU（显存/GPU 数/时间）。各类任务用独立并发池，避免论文解析堵住 GPU 实验或反之。任务调度要支持项目内并行、每个 idea 的并行上限、GPU 资源请求/释放、队列公平性和优先级；一个失败或等待资源的 idea 不阻塞其他可执行 idea。每次准入都结合实时机器快照、任务资源估值和用户配额重新决策；资源不足就排队，不能只根据服务器 GPU 总数静态配置并发数。

### Checkpoint 与恢复协议

checkpoint 分为三层，不能把“会话能 resume”误认为整条科研工作流可恢复：

1. **工作流 checkpoint**：每个阶段的输入快照、配置/提示/schema/模型版本、已完成节点、产物引用和状态写入持久化数据库。阶段间只传不可变 artifact ID；论文处理以单篇 PaperCard/小批次为恢复单元，baseline 以方法+配置+数据切分为单元，idea 以 idea 版本+实验规格+运行编号为单元。
2. **任务 checkpoint**：每个 task 在开始前持久化 `queued → leased/running → committing → succeeded` 等状态，运行中定期 heartbeat；同时记录尝试次数、租约过期时间、取消原因和日志位置。Worker 崩溃后，过期租约回到队列，只重试该任务。提交产物采用临时文件写入、校验哈希后原子 rename，再提交 DB 成功状态；启动时扫描并清理/隔离未提交临时产物，修复“文件已写完但 DB 尚未提交”等情况。
3. **训练 checkpoint**：长时间模型训练在实验适配器支持时按时间/步数保存模型、优化器、scheduler、随机数状态、epoch/step 和配置，可从最近一次安全点续训。算法或环境不支持安全恢复时，崩溃最多重跑当前单个实验 run；已完成的论文、baseline、其他 idea 和既有实验结果都不重跑。

所有阶段设计成幂等：相同输入哈希、配置和版本重复提交应命中已完成结果；输入、prompt/schema、模型或代码版本变化只使依赖该版本的下游节点失效。外部模型请求采用可用的幂等键，记录 request/response 状态和成本；若请求发出后进程在保存结果前崩溃，允许只重做该次模型 task，并明确可能出现的重复 API 费用，不能因此重做整个阶段。

安全退出（`Ctrl-C`/`ideaseek pause`）先停止领取新任务，向运行任务发取消/收尾信号，保存可保存的训练 checkpoint，完成已开始的原子提交并释放资源；强制 kill、OOM、断电等情况由租约超时和启动恢复扫描收敛。恢复时重新探测 GPU/Python/容器环境；环境或输入发生变化则暂停受影响任务并提示，不拿旧 checkpoint 在不兼容环境中盲目续跑。

checkpoint 的可靠性还依赖存储本身：数据库按配置定期备份，重要 artifact 用哈希清单核验；提供项目状态与任务元数据的可移植备份/恢复命令，并定期验证能从备份恢复。备份策略要说明保存位置、保留周期和磁盘需求；工作目录与备份不能只放在同一块易损磁盘上。没有完成恢复演练前，不宣称具备灾难恢复能力。

同一项目锁防止重复启动冲突；`resume` 只重跑失败、租约失效或依赖输入/版本变化的最小节点。每个节点输出做内容哈希缓存，模型输出缓存键包含模型、prompt、schema 和来源片段版本。GPU Worker 启动时声明设备和资源；一张卡、多张卡和零 GPU 都使用同一接口。先支持单机多 GPU；多服务器时再把队列和 artifact store 外移，Worker 远程拉取任务。

每个项目实现资源预估与硬配额：最大模型费用/token、最大 GPU 小时、最大墙钟时间、磁盘上限、并发数、每个 idea 的实验轮数。状态命令显示已用/剩余预算。磁盘写满、GPU OOM、模型限速、断网和进程被杀必须有明确错误类别及恢复策略。日志做轮转，产物保留策略可配置；清理只删平台拥有且已登记的缓存/临时目录。

## 9. 安全、版权与数据边界

- 实验容器使用非 root 用户、只读输入、独立输出目录、CPU/内存/显存/时长限制；默认禁网络，只有配置许可的依赖预下载阶段可联网。
- 用户 clone 的 comparison 仓库及其中脚本都视为不可信代码；只在隔离容器中检查、构建和运行。保留原始仓库快照，Agent 修复在工作副本进行，patch 及依赖下载均可审计。
- 不向 Agent 暴露服务器密钥；模型 API 凭据由宿主 credential store 注入请求，不写入日志或容器环境。
- Agent 生成文件限定在 `workspace/`；执行前保存 git diff，保留用户文件和原始论文不变。
- PDF 正文视为不可信数据，提示注入内容不可作为系统指令；工具权限通过白名单发放。
- 论文全文只用于用户授权的研究项目，报告优先输出分析、短引用和定位，不复制大段论文原文；遵守机构授权和数据治理规则。
- DSH 官方将项目标注为 developer preview 且未经安全审计；它自己的权限/沙箱不是唯一隔离边界，必须外部容器化并固定版本。
- 配置明确标注哪些内容会发往第三方模型 API；对未公开论文、专有数据或受限数据，支持纯本地模型/禁外发模式，并在 `doctor` 中提示实际生效的模型端点。
- 记录数据集来源、版本、许可证/使用限制和哈希；不得默认把用户的私有数据打包进可分享报告或容器镜像。

## 10. 报告与交付物

最终每个候选方向生成：

1. **研究地图**：论文覆盖范围、主题与方法谱系、代表工作、证据缺口。
2. **Idea 报告**：候选及排序、最近邻工作、新颖性证据/不确定性、反方意见和停止理由。
3. **实验结果**：数据版本、每个 comparison 的来源/复现状态、初始基线结果、各基线与候选的对齐指标、消融、种子/方差、失败实验与结果解释。
4. **可运行代码**：独立 git 分支或 commit、环境文件、运行命令、数据准备说明和测试。
5. **可复现清单**：输入文件哈希、解析/提示/模型版本、实验镜像、硬件、配置、日志、产物引用。

平台把“真正可用的 idea”表述为经小规模验证且证据充分的候选，并注明外推边界；最终新颖性与科学有效性仍须研究者确认。

## 11. 平台自身的质量评估

平台必须有独立于真实用户项目的评测集和回归集，否则很难知道某次 prompt、模型或解析器升级是进步还是退步。维护一组人工标注论文/事实/证据跨度、已知相关工作对、已知方法复现任务和固定实验项目。逐版本测量：

- 文献解析完整率、字段准确率、关键结论证据支持率、页码定位准确率；
- 检索对人工标注相关论文的 Recall@k，尤其是候选 idea 的最近邻工作覆盖率；
- Idea Card 的事实错误率、重复率、研究者盲评价值/可检验性，而不是把 LLM 自评分当质量指标；
- 固定环境重跑的一致性、基线复现误差、实验无效率与预算偏差；
- 单篇论文成本、单个候选 idea 成本、端到端耗时，以及失败/重试比例。

提示词、解析器、模型或索引变更须通过回归集；保留版本和结果，避免静默质量回退。匿名/人工反馈经明确配置后才能用于平台评测，不默认将实验室论文和数据汇入共享语料。

## 12. 首次运行的验收与人工信任

平台第一次进入新领域时，应先以小批量语料（例如 20–50 篇）产出一份“校准报告”：抽样论文卡片、解析失败清单、代表性方法、研究者确认的关键术语/任务边界。研究者可以修正术语、忽略范围外论文或补充缺失工作，再继续全量处理。此阶段能发现方向理解偏差，避免对 1000 篇论文高效地产生错误综述。

报告中将事实、推断、假设和建议显式区分；展示证据链接与置信/不确定性原因。所有关键结论可以从报告跳转到 PDF 页码/片段，idea 到论文证据、实验规格、代码提交、运行结果构成完整 provenance 链。

## 13. MVP 范围与里程碑

### M0：CLI 与可恢复项目

完成 `init/setup/doctor/next/run/status/attach/watch/events/pause/resume/cancel/report`、DSH profile/插件加载、凭据引用与最小权限网络策略、输入哈希清单、状态数据库、持久化 RunEvent 流、后台 supervisor、日志和暂停/恢复。用故障注入验证：前台终端断开、后台 supervisor 重启、多个客户端 attach/replay、Worker 在解析中崩溃、Agent 在模型请求前后崩溃、写 artifact 时崩溃、GPU 训练中 OOM/强杀、整机重启、用户中途更新输入；确认只重跑当前未完成或失效的最小单元，已完成产物不丢失、不重复计费/运行（模型请求边界需明确记录可能重复的单次调用成本）。完成一次从备份恢复的演练，并校验恢复后任务状态与 artifact 哈希；用假的/最小权限 GitHub token 验证 secret 不进入 prompt、日志和容器。

### 首个领域验证方向

本计划把目录、Agent、协议生成和任务调度设计成通用能力；具体领域适配器不是通用平台开发的前置条件，而是用来验证协议生成器和执行器是否可靠的领域插件。联邦学习模型异构可以作为第一个真实验证方向，由论文、comparison 代码和用户数据自动生成具体协议。多模态早期预测、短视频、图像分割和联邦学习域泛化后续复用同一底座，按需要增加解析器和检查器。不能因为同一台 Linux 多 GPU 服务器能启动代码，就声称所有方向都已经具备可靠科研能力。

### M1：论文证据管线

支持 PDF 入库、解析/去重、全文检索、PaperCard schema、页码证据校验和研究地图。先用 30–100 篇领域论文进行人工抽样核验，不从千篇规模起步。

### M2：idea 评估

产出多个 Idea Card，相关工作反查、反方评审、评分解释与人工反馈入口。验证候选能否准确区分与已知方法，而不是只看文本是否听起来新颖。

### M3：受限实验闭环

支持 `comparisons/` 方法清单、从论文自动发现候选、clone/官方代码导入、论文重实现、环境诊断、沙箱内有预算的修复循环与隔离运行；加入固定数据协议、单一小数据集、实验容器、代码版本化、指标归档、失败分类和最多 N 轮 idea 迭代。跑通原样可运行、兼容性修复后运行、重实现、算法语义改动需单独确认、候选被支持/否证和无效运行等路径。

### M4：扩展吞吐

经质量评估后提升到数百/千篇论文；增加多模型路由、本地 vLLM、多 GPU Worker、文献格式兼容和成本观测。

每个里程碑都应有人工 gold set：抽查解析字段和证据准确度，测论文覆盖与重复率，检查 idea nearest-work recall，验证实验可复现。数量吞吐不是首要验收指标。

## 14. 首版技术选择建议

- **CLI/控制层**：选择 Python 主入口（Typer）以降低与解析/实验 Worker 的集成成本；通过 DSH Python SDK 或受控子进程驱动 DSH。若 DSH 插件开发必须 TS，则 TS 插件调用 Python 控制服务的稳定协议。
- **工作流存储**：单人/单机先 SQLite WAL；一旦并发 Worker 或多用户使用，切 PostgreSQL。任务接口从一开始抽象，避免业务绑定 SQLite。
- **文件与检索**：原始文件/产物用本地文件系统；正文先用 PostgreSQL 全文搜索 + 可替换向量索引，规模和评估证明需要后再拆专用搜索服务。
- **实验执行**：容器运行时抽象；首版 Linux Docker/Apptainer 选服务器可用的一种，统一 RunSpec。
- **模型调用**：直接使用 DSH provider；保留内部接口以便未来接入其他 provider，但 Pi 不属于 MVP 依赖。

### 平台支持策略

首版把 **Linux（优先 Ubuntu 服务器）作为正式科研执行平台**：论文处理、Python Worker、Docker/Apptainer、CUDA、多 GPU 调度、代码修复和实验容器都以 Linux 为基准验收。实验室服务器通常是 Linux，科学计算依赖和 GPU 容器生态也更稳定；先保证这一条链路可靠，比同时维护两套原生执行环境更重要。

Windows 分三层支持：

1. **Windows + WSL2**：作为推荐的个人开发/本地测试方式，尽量复用 Linux Worker 和容器流程；文档说明项目应放在 WSL2 Linux 文件系统中，避免跨文件系统 I/O 开销。WSL2 的 GPU、容器和驱动仍需通过 `doctor` 检查，不能把它当成所有服务器配置都相同。
2. **Windows 原生 CLI/论文分析**：可支持初始化目录、PDF 解析、知识库查看、状态/报告和不依赖容器/GPU 的任务。路径、进程、信号、软链接和 shell 命令通过平台抽象层处理，不在业务代码中写死 POSIX 命令。
3. **Windows 原生 GPU 实验**：不作为首版完整承诺。只有为 Docker/Apptainer、Python/CUDA、进程隔离和资源探测建立明确适配器并通过回归测试后，才标记为支持；否则 `doctor` 明确提示使用 WSL2 或 Linux 服务器。

核心数据格式、任务协议、checkpoint、知识库和报告必须跨平台可移植；平台路径使用 `pathlib`/Node path API，容器命令和资源探测由 OS-specific adapter 实现。每个实验记录 OS、内核/WSL、容器运行时、Python/CUDA 和 GPU 环境，恢复时重新验证兼容性。不要在 Windows 上伪装 Linux 实验结果，也不要让 Windows 的路径或环境信息进入可复现 Linux 命令而未被标记。

以上选型以实验室“单台 Linux 服务器、一个研究用户/项目、存在 GPU”作为 MVP 假设。确认服务器上的容器权限、存储和模型接口后再定部署脚本；Windows 首版目标是能准备项目、检查状态、进行轻量分析并通过 WSL2 连接/运行 Linux 执行环境。

## 15. 关键风险与缓解

| 风险 | 缓解设计 |
|---|---|
| PDF 解析错，导致后续推理建立在假事实 | 证据定位、解析质量标记、关键字段核验、抽样人工 gold set |
| Agent 凭空声称 idea 创新 | 最近邻检索、对抗式 novelty challenger、引用支撑与不确定性说明 |
| 多 Agent 共识只是重复同一偏见 | 角色隔离、独立生成、证据约束和反方审查；模型/提示多样性作为可选项 |
| 单次小数据实验过拟合或泄漏 | 预登记判据、固定划分、基线复现、多个种子/方差、明确外推边界 |
| 失败循环烧光算力与 API 预算 | 每项目硬预算、实验最大轮次、停止条件、人工配置优先级 |
| 生成代码破坏服务器或泄露数据 | 一次性容器、最小权限、默认禁网、凭据不入容器、原始目录只读 |
| DSH 更新破坏插件 | 锁版本、兼容性测试、HarnessAdapter、业务数据与 Agent Runtime 解耦 |
| 论文规模扩大后成本/时间失控 | 去重、增量索引、内容哈希缓存、按需检索、有限 Worker 并发 |
| 语料范围不完整却误报“创新” | 声明查新边界；支持可审计的外部检索，并把覆盖不足作为报告限制 |
| 反复在同一验证集调 idea 造成虚高 | 区分探索/确认数据、登记尝试次数、保留独立确认实验 |
| 模型/提示升级令质量悄悄退化 | 固定 gold set 回归、记录版本与质量指标、变更可回滚 |
| 私有论文或数据意外发到外部模型 | 明示端点和外发策略；提供本地模型/禁外发选项与数据分级 |
